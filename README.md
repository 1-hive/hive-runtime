# hive-runtime

How agents do work on a hive record: launching workers, dispatching independent reviews, supervising stuck work, cleaning up, and the chief of staff's tools. It's the operating loop from 1-hive's plan (Phase E), a minimal form of One Hive release R6.

**Status (2026-11-10, v0.5.60):** runs live on 1-hive and on the proto-hive (long-lived Iter and OpenClaw bots, reviews routed by tier to long-lived reviewers). Workers wait for their independent review in their own session (One Hive R5, `docs/review-contract.md`). Originally (2026-10-19) extracted from [1-hive](https://github.com/1-hive/1-hive) with its history. Paths and ids are configuration (below); 1-hive runs it with the defaults. Long-lived agents (Iter) work through [`adapters/iter`](adapters/iter/README.md), next to the per-task launcher.

- **Launching work:** `launch-task.sh` (one attempt per assigned task, in the agent's own rootless container, routed by hive-route), `watch-task.sh`, `load-skills.sh`, `agent/` (the agent image), `agent-users.sh` (one OS user per agent).
- **The loop:** `dispatcher.py` (launches workers and independent reviewers), `supervisor.py` (nudges, restarts, reassigns, escalates), `sweeper.py` (removes task folders the record no longer needs).
- **The chief of staff:** `hive-mcp.py` (an MCP server over the record, plus `floor`: what each agent is doing now, from hive-bridge's Floor at `HIVE_FLOOR_URL`), `docs/chief-of-staff.md` (its role on 1-hive) and `docs/chief-of-staff-proto-hive.md` (on the proto-hive: no goals, a work group, long-lived agents), `cos.sh` (its container; `COS_ROLE_DOC` picks the role doc: rootless Podman with keys as secrets, or, with `HIVE_CONTAINER_RUNTIME=docker`, plain Docker with the keys bind-mounted read-only; the Docker path isn't exercised on 1-hive).
- **Isolation:** `agent-ports.py` (the only host services containers reach), `git/` (per-actor git over SSH, with a pre-receive hook that keeps pinned commits reachable).
- **The operator:** `op`, short commands that sign with the operator's key.
- `skills/hive-worker/`: the worker contract (`SKILL.md`: what a worker or reviewer must do on the record) and its scripts `review-wait.py` and `result-refs.sh`, as an Agent Skills skill.
- **Skills (One Hive R4):** [`docs/skills.md`](docs/skills.md). Every attempt loads the hive's registered skills for its role and harness from its skills registry ([hive-skills](https://github.com/1-hive/hive-skills): content-hashed, expiring entries; the loader refuses duplicates, conflicts, expired skills and pins that don't verify) into the task folder, and keeps the set's digest with the attempt. `op skills` shows the registry and any drift. Test: `tests/load_skills_test.py`.
- **Independent review (One Hive R5):** [`docs/review-contract.md`](docs/review-contract.md), how a worker invokes a review, what the reviewer receives and how the verdict is recorded. A worker posts its result and waits for the verdict in its own session (`review-wait.py`, copied into each task folder); a failed review comes back to that session, up to 2 times per attempt, before the supervisor restarts the task. `op review <task> [reviewer]` asks for a review by hand (again, for a second opinion). Tests: `tests/review_wait_test.py`, `tests/review_in_session_test.py`.
- **A fresh attempt after the supervisor gives up:** a task restarted 3 times is escalated to the operator (`repeated_failure`). `op restart <task> [note]`, or **🔁 Restart** on the Telegram alert (hive-bridge v0.5.41), resolves the escalation with `Restart: <note>`; the supervisor then restarts the worker (stopping it first if it still runs) with the note in its restart context, and counts its attempts anew. Only the operator's resolution counts. On a task that isn't escalated (e.g. to move it to the model a new route override names), `op restart` asks the supervisor directly (`.route/<task>/restart-request.json`); either way the record's `task.restarted` says "the operator asked for a fresh attempt", and a worker that ended on its own gets how it ended (stopped from outside, killed, lost its connection) in its reason. Test: `tests/op_restart_test.py`.
- **`main-watch.py`:** where agents could push to `main` but by agreement don't (they push a branch and a human merges the pull request), flags commits that reach `main` without a passed review on the record, after the fact; from a timer, alerts through e.g. hive-bridge's `telegram-say.py`. `--registry R --under DIR` watches every registered repository cloned under DIR, on its default branch; `--also NAME:BRANCH` adds another branch of one of them (a line agents track besides the default, e.g. `iter:protomega`). Test: `tests/main_watch_test.py`.
- **[`docs/long-lived-agents.md`](docs/long-lived-agents.md):** how to put a hive of long-lived agents (chat bots) on the record: sidecars, delivery per kind of agent, keys when agents share a user, self-modification, repositories, pitfalls.
- **`publisher.py`:** for staged repositories (the registry lists a hive copy first): results wait in the hive copy until their review passes, then this pushes the reviewed commit to the repository's home as `hive/<task>` (after a scan for secrets and `--deny` patterns) and posts the pull-request link; it also mirrors each home into its copy. From a timer. `docs/long-lived-agents.md`, "Review before publishing". Test: `tests/publisher_test.py`.
- **`new-repo.py`:** an operator's tool to start a new code repository for the agents: creates it on GitHub with the publisher's token, adds the publisher's push key, invites the `--collaborator` logins with write access (the people who merge its pull requests), registers it staged, commits the registry to a bare registry repository (`--registry-repo`) and prints the digest the operator records. **`registry-pull.sh`** keeps another machine's copy of the registry current from that repository (root, from a timer). `docs/long-lived-agents.md`, "Code repositories". Test: `tests/new_repo_test.py`.
- **`adapters/install-agent.py`:** puts a long-lived agent on the hive, or takes it off (`--undo`): the hive channel and tool (Iter) or `hive-task`, its skill, the allowlist entry and heartbeat line (OpenClaw), and the hive rule (`adapters/hive-rule.txt`) in its prompt; idempotent, with a `.pre-hive` backup of each file it changes. Test: `tests/install_agent_test.py`.
- **`adapters/openclaw/hook-deliver.py`:** an OpenClaw agent's sidecar delivers each message from the record straight into the agent, as a turn through the gateway's inbound webhook (`/hooks/agent`, its own token, one agent only, nothing posted to chat), instead of waiting for the agent to look; `install-agent.py openclaw --hook-token-file F` enables the webhook. Test: `tests/hook_deliver_test.py`.
- **Model accounts at their limit:** `claude-failover.sh` runs headless Claude Code (`claude -p`) on the first account in `CLAUDE_TOKEN_FILES` that isn't at its usage limit, marking a limited account for `CLAUDE_FAILOVER_COOLDOWN` (1800 s) and rerunning the call on the next; `cos.sh` uses it when `COS_KEY_DIR/claude-oauth-token.2` exists. `adapters/openclaw/add-claude-account.sh` gives an OpenClaw gateway's agents a Claude subscription as a further Anthropic account (OpenClaw rotates to it on a billing or usage limit; `status` lists accounts without secrets). Sidecars and reviewer runners report an account out of usage, spend or credit in their beacon ("its model account hit a usage limit: …"), so the Floor shows the agent can't run; review routing then treats every reviewer on the same account as unavailable. Tests: `tests/beacon_test.py`, `tests/reviewer_limit_test.py`, `tests/review_route_sim.py`.
- **Machine tools:** `adapters/reviewer/add-reviewer.sh` adds a reviewer runner modelled on one already running on the machine (its own user and record key, another model): `setup` prints the public keys to register, `start` clones the workspace and starts the unit. `adapters/upgrade-popos.sh` brings proto-hive's pop-os to a hive-runtime tag (refreshes the installed hive files, restarts sidecars and idle reviewer runners; the bots stay up).
- **Long-lived agents:** `adapters/iter/`, a `hive` channel and a `hive_task` tool for Iter agents (spawned daemon, or a sidecar outside the agent); `adapters/openclaw/`, the `hive-task` command and a skill for agents with a shell; `adapters/reviewer/`, a runner for a reviewer behind a command (Astra); `adapters/iter/time_split.py`, how much of an agent's model time went to record tasks. Sidecars and the reviewer runner post signed **beacons** (what the agent is doing now, from its own files; never message text) to hive-bridge's Floor: `adapters/iter/README.md`, test `tests/beacon_test.py`. All tested end to end on a scratch record: `tests/iter_adapter_e2e.py`. `adapters/iter/conformance.py` checks that a given Iter agent (any variant) works with the adapter, through its own `--invoke` worker and limits; test `tests/iter_conformance_test.py`.

**Beyond R6 (our addition):** context capture. New runtime work builds an agent's context only from pins, or stores what it adds under content hashes off the record and pins one digest on the result, so R9 can replay and diff runs. Not in the shared roadmap; not yet built into the existing adapters. 1-hive PLAN.md, D17.

Related: [hive-record](https://github.com/1-hive/hive-record) (R1 + R2), [hive-bridge](https://github.com/1-hive/hive-bridge) (where humans meet the hive), [hive-route](https://github.com/1-hive/hive-route) (R8), [hive-pin](https://github.com/1-hive/hive-pin) (R0).

## Configuration

Every tool reads the same environment variables (`paths.sh` for the shell tools, `hive_paths.py` for the Python ones). The defaults are 1-hive's layout, so 1-hive sets none of them; another hive sets the ones that differ, e.g. in its systemd units.

| Variable | Default | What it is |
|---|---|---|
| `HIVE_ID` | `1-hive` | The hive's id on its record |
| `HIVE_GATEWAY_PORT` | `8470` | The record gateway's port on the host. Inside an agent container the record is always at `127.0.0.1:8470` (`agent/hive-entry`) |
| `HIVE_URL` | `http://127.0.0.1:$HIVE_GATEWAY_PORT` | The record gateway, from the host |
| `HIVE_CONFIG_DIR` | `~/.config/hive` | Keys and secrets: `agents/<actor>.key`, `operator.key`, `claude-oauth-token`, `gateway.env`, `route-overrides.json` |
| `HIVE_WORK_DIR` | `~/work/1hive` | Task folders, and the tools' state (`.ports`, `.route`, `.supervisor`, `.sweeper`, `cos`) |
| `HIVE_REPOS_DIR` | `~/repos` | The hive's git remotes, `<name>.git` |
| `HIVE_DEPLOY_DIR` | `$HIVE_REPOS_DIR/1-hive/deploy` | The hive's declared configuration: `registry.json`, `route-table.yaml`, `route-sources.yaml`, `review-allowlist.json`, `runtime` |
| `HIVE_WORKSPACE_REPO` | `$HIVE_REPOS_DIR/hive-workspace.git` | The workspace remote (orders, reports, questions) |
| `HIVE_ROUTE_DIR` | `$HIVE_REPOS_DIR/hive-route` | The router's checkout |
| `HIVE_DEFAULT_REPO` | `mtg-player` | The code repository every task folder holds; others come as `EXTRA_REPOS` |
| `HIVE_LONG_LIVED_ACTORS` | (none) | Comma-separated actor-id patterns (`worker.*,reviewer.astra`) that are never launched or restarted: their sidecar or runner takes work from the record. The dispatcher only assigns reviews to them; the supervisor nudges, then escalates to the chief of staff, and escalates a result whose review waits over `HIVE_REVIEW_WAIT_SECONDS` (7200) |
| `HIVE_REVIEWERS` | `reviewer.codex.1,reviewer.claude.1` | The reviewers the dispatcher assigns, in order of preference (without a review route table, or when the router gives no route) |
| `HIVE_REVIEW_ROUTE_TABLE` | (none) | A hive-route table (rev 21) whose review routes name their long-lived `actor`: the router picks each result's reviewer by the review's tier (the order's `Route facts:` and `Review tier:`), RT4 against the author and the Floor's view of who can run (`review_routes.py`; hive-route ROUTING.md §9.5) |
| `HIVE_REVIEW_ROUTE_SOURCES` | (none) | The sources file naming its qualifications file (`hive-route canary accept TABLE ROUTE --no-canary`) |
| `HIVE_REVIEW_ROUTE_LOG` | `<work>/.route/review-route-log.jsonl` | Where the review decisions are logged |
| `HIVE_REVIEW_MOVE_SECONDS` | 600 | A routed result waiting on a reviewer the Floor has shown unable to run (or offline) this long is moved to the reviewer the router picks then |
| `HIVE_FLOOR_URL` | `http://127.0.0.1:8476` | hive-bridge's Floor, read by the chief of staff's `floor` tool and by review routing |

Two need care, because they're read outside the operator's session:
- `git/hive-git-shell` runs as sshd's forced command, with a clean environment. A hive whose repositories aren't in `~/repos` writes `HIVE_REPOS_DIR=…` into the forced command.
- `agent-users.sh` runs under `sudo`: pass `HIVE_WORK_DIR` on its command line when it isn't the default.
